# F08 engine control API and data services

Date: 2026-11-15. Self-reported; no independent review. Built on the provisional F06/F07 foundation (decision 0002).

`@browser-vr-engine/control` provides:

- **Host-injected identity:** HMAC-SHA-256 signed engine grants (`v1.<claims>.<sig>`) with subject, tenant, project (or `*`), engine capabilities, audience, issue/expiry and id. Verification supports secret rotation, clock skew, audience and expiry. WebCrypto only, so hosts and browsers share the format. Product roles never enter the engine: hosts map their roles to capabilities (XLR8 does this in C02/C05).
- **Namespaces and capabilities:** every API call derives tenant from the verified grant; project scoping and per-capability checks; non-workspace access returns 404.
- **Control API:** framework-agnostic `handle(request)` for workspaces, versioned documents (`If-Match` compare-and-swap), objects (sha256 integrity, attachment download headers), idempotent jobs (`Idempotency-Key`) and an audit hook.
- **Data services:** memory adapters (local/offline hosts) and Postgres adapters over an injected SQL client: documents, a bytea object store, and a job queue with leases (`FOR UPDATE SKIP LOCKED`), retries and request-hash idempotency. Migrations roll forward/back; a failed run leaves the schema exactly as before.

Tests: the same contract suite runs against memory (`npm test`) and real PostgreSQL (`npm run test:integration`, required `engine-integration` workflow with a `postgres:17` service): tenant isolation, concurrent CAS, idempotent retries (8 concurrent submits, one job), lease races and reclaim, token expiry/audience/forgery, migration forward/rollback/failed-step recovery, object corruption detection. Locally against PostgreSQL 16: 7 memory + 7 integration tests passed.

Not done: a hosted object store (S3-compatible adapter) and a queue worker runtime; both fit the interfaces. No deployment of a control service (static site only; no new Render services).
